### 1.9 Per-function Kotlin golden-vector layout rationale (for the evidence record)

`android/app/src/test/java/com/hasta/app/domain/features/FeatureGoldenVectors.kt`
(170 KB, generated) does **not** hold all cases in one initializer. The generator
(`research/features/golden.py`, `render_kotlin`) emits one private function per
golden case (`case_first_frame_right()` … 20 total) collected by
`val cases: List<Case> = listOf(case_…(), …)`. Rationale, documented inline in
the generator and in commit `8964acb`: a single `listOf(...)` big enough to
exceed the **64 KB JVM method bytecode limit** fails to compile with
`MethodTooLargeException` in `<clinit>` once the extreme-scale cases
(commit `a9f84e4`, blueprint §6.5) are included. One function per case keeps each
method small; the public `cases` list preserves the test-facing API.

## 5. Dataset adequacy assessment

Current inventory (`research/data/manifest.json`, verified locally):

| Clip | Label | Frames | Signer | Source |
|---|---|---:|---|---|
| `INCLUDE-radio-001` | `radio` | 56 | `INCLUDE-dataset` | INCLUDE, Zenodo 4010759, CC BY 4.0 |
| `SELF-webcam_hand-001` | `webcam_hand` | 407 | `SELF` | local webcam (smoke test) |
| `SELF-webcam_smoke-001` | `webcam_smoke` | 51 | `SELF` | local webcam (smoke test) |

- **Usable ISL sign classes: 1** (`radio`). `webcam_hand`/`webcam_smoke` are
  smoke-test labels, not vocabulary signs.
- **Samples per class: 1.**
- **Distinct signers: effectively 1 real human (`SELF`) + one dataset-wide
  aggregate ID (`INCLUDE-dataset`) that collapses many signers into one label.**
- **Signer-independent train/validation/test splits: impossible** with this data.
- **Class imbalance:** extreme (3 classes × 1 sample). No missing labels, but
  most labels are non-sign test artifacts.
- G11 passing on one extracted clip proves the *pipeline*, not training adequacy.

**Minimum additional data required before any M2 training (order-of-magnitude):**

1. A locked vocabulary of 20–30 ISL signs (gloss, stable ID, English caption,
   documented meaning).
2. ≈30–50 consented clips per sign per the capture/extract pipeline
   (≈600–1,500 clips total), each recorded with a **per-signer** `signer_id`
   (the `landmarks-v1` metadata schema already supports it).
3. ≥5 distinct signers so a signer-independent evaluation is statistically
   meaningful (held-out signers).
4. An idle/transition corpus (hundreds of short clips of rest motion and
   between-sign transitions) for the anti-flicker state machine.
5. Unknown-sign negatives (other signs + non-sign hand motion) for rejection
   threshold calibration.
6. Deterministic, recorded split tooling (split assignment stored in the
   manifest) before any model is trained.

The INCLUDE dataset (Zenodo 4010759, CC BY 4.0) can be scaled up, but whether it
carries usable **per-clip signer annotations** must be verified against the
source dataset itself — it is not recorded in this repository, and signer
identity cannot be recovered from the current aggregate `signer_id`.

   manifest; audit green.
5. **M2.4 — Training stack:** torch as a pinned optional extra in
   `research/`; GRU and 1D temporal CNN implementations; one shared
   train/eval protocol on identical splits; metrics report (per-sign and
   aggregate, signer-independent).

   emission state machine; false-accept/false-reject reporting.
7. **M2.6 — LiteRT export:** convert winner; parity harness PyTorch vs LiteRT on
   golden inputs (mirroring the features-v1 parity pattern); tolerance documented.
8. **M2.7 — Live wiring:** wire `FeatureExtractor` into the live pipeline (closes
   G14), on-device inference, resolver returning sign ID + caption, end-to-end
   latency logging via the existing benchmark infrastructure.

## 8. Risks and acceptance criteria

| Risk | Mitigation / acceptance criterion |
|---|---|
| Dataset scale-up is the critical path | M2.4 cannot start until ≥20 signs × ≥30 clips × ≥5 signers exist with audited manifests; treat as the gating milestone |
| Signer leakage in evaluation | Splits must be signer-independent and recorded in the manifest; acceptance: held-out signers never appear in training |
| Single-signer bias from self-capture | Self-capture alone cannot satisfy signer independence; multi-source data required |
| CI action breakage (third-party actions, Ubuntu 26 migration) | Pinned majors, drift-checked local script as the source of truth; re-verify after runner-image migrations |
| Feature drift after M2 wiring | features-v1 is immutable; any change requires features-v2 + ADR + new golden vectors |
| Overclaiming recognition quality | Report per-sign and signer-unknown metrics; no claims beyond the evaluated vocabulary (blueprint §risk table) |
